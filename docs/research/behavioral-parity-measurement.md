# Measuring behavioral and audio parity

Research date: 2026-10-13. Read-only review of the current Halftrack source and tests, plus first-party documentation and public SDK source. No proprietary binary, bundled content, or reference application was inspected for this report. This report specifies proposed work; it does not certify a completed comparison.

## What a defensible parity claim means

The present preview establishes several useful Halftrack behaviors, but has no automated paired reference-output corpus. Passing its own tests therefore establishes internal correctness for those cases, not equivalence to another DAW. “Zero differences” would need an explicitly bounded version/platform/configuration and observable contract; a finite test suite cannot establish equivalence for every possible session, third-party plug-in, hardware device, and future version. This is a methodological conclusion, not a legal conclusion.

Binary analysis can provide evidence about particular compiled functions, constants, call relationships, or state transitions. A decompiler does not reconstruct a finished cross-platform application project. Ghidra documents function-level conversion to a high-level C representation, inferred types, and changes to output based on analyst annotations. Its representation can contain hidden parameters absent from source. **Inference:** a plausible decompiled expression must still be checked against the actual machine behavior and independently measured output; it is not proof of recovered original source or whole-program equivalence. [Ghidra's own decompiler documentation](https://github.com/NationalSecurityAgency/ghidra/blob/master/Ghidra/Features/Decompiler/src/main/doc/decompileplugin.xml).

Keep three distinct acceptance levels:

1. **Exact observable behavior:** integer sample positions, event ordering, state transitions, channel routing, persistence, and undo results agree for a declared fixture.
2. **Bit-identical audio:** decoded sample words agree for an explicitly deterministic path, after only its specified latency compensation. Compare PCM, not complete WAV bytes, because container metadata can differ.
3. **Measured audio similarity:** report numerical error, spectrum, temporal behavior, and listening results for a DSP path that does not meet bit identity. Never label a numerical tolerance “zero differences.”

The reference's public audio fact sheet itself distinguishes transparent operations from transformations, documents controlled cancellation tests, and specifies a sinusoidal pan law with unity center and approximately +3 dB at the extremes. Its neutral-render assumptions exclude signal changes such as stretching, rate conversion, dither, and fades. Use these descriptions to define separate fixtures, not one universal null-test expectation. [Official version 12 audio fact sheet](https://www.ableton.com/en/live-manual/12/audio-fact-sheet/).

## Concrete gaps in the current source

Reviewed source locations below refer to the checkout read on the research date; they are observations of source/tests, not freshly executed measurements.

| Area | Current evidence | What the evidence misses |
| --- | --- | --- |
| **Pan law: a concrete likely sound mismatch** | `src/Session.cpp` does not choose a pan law. The pinned engine defaults to `PanLawLinear`; its implementation gives left/right gains `gain * (1 - pan)` and `gain * (1 + pan)`. Hard panning therefore doubles the retained channel, approximately +6.02 dB relative to center. | This differs from the published reference description above. `tests/SessionTests.cpp:219` only checks that the right channel becomes quiet and left remains above 0.1, so it accepts either law. Measure a full matrix before changing existing project semantics. |
| Mixer comparisons | `tests/SessionTests.cpp:99` compares generated sine outputs against expected gain, with maximum error below 0.0001. | It discards the first 4096 and final 1024 samples: approximately 85.3 ms and 21.3 ms at 48 kHz. Attack, dezippering, clip-edge fades, truncation, and delay errors in those windows can escape. |
| MIDI timing | `tests/MidiTests.cpp:160` verifies a note at beat one in a 120 BPM clip begins between samples 24000 and 24002 at 48 kHz. | The test measures audible threshold crossing, not received note-event time. Oscillator phase/filter/envelope can shift threshold crossing. Only one onset, tempo, sample rate, render block setting, and graph topology are covered. |
| Transport and tempo | `Session::setTempo` edits the first tempo item; `setLoop` persists loop bounds. | No event trace for seek, mid-block loop wrap, tempo ramps, meter changes, start inside held notes, chase, or rapid stop/restart. Current loop test verifies state/undo, not rendered loop-boundary correctness. |
| Built-in synth | Sixteen independently calculated filter samples, pitch, sustain/release, voice limits, and block partitioning are tested. | No paired target-device sound tests; no complete oscillator/ADSR/filter grid, aliasing benchmark, velocity curve, denormal tail sweep, or repeated-note ordering matrix. The MIDI dispatcher handles notes/controllers, not pitch-bend or channel-pressure messages. |
| DSP parameter timing | A bounded FIFO transports complete synth settings; the callback drains it at the start of a block. | FIFO packets have no sample timestamp. This is suitable for current manual controls, but does not establish sample-timed automation. Smooth changes and abrupt changes need distinct tests. |
| Plug-ins | `tests/TestGainPlugin.cpp` is a deterministic scalar gain fixture, with state and bypass coverage. | No nonzero/dynamic latency, tail, sidechain, multi-output, instrument-event, transport-context, state-chunk, crash/hang, or offline-mode fixtures. AU is enabled but not tested here; CLAP hosting is unfinished. |
| Export | `Session::exportWav` currently sets `blockSizeForAudio = 512`; WAV length, basic signal, cancellation and graph lifetime are covered. | No identical offline-versus-callback capture comparison; no render-block matrix; no reference rate-conversion/dither tests. The tail-duration test uses a dry source, so it does not validate a decaying effect tail. |
| Recording | Synthetic stereo input reaches the real recording graph. | Test driver declares zero input/output latency, runs 48 kHz/256 only, and checks duration within 0.8–1.3 seconds plus nonzero amplitude. It does not establish exact sample placement or captured PCM identity. |
| Persistence and undo | Stable IDs, notes, synth state, portable media, atomic-save failure handling and controlled VST state round trips are exercised. | Most sequences are hand-selected. Full gesture grouping, save/edit/undo dirty semantics, arbitrary state-only plug-in edits, format migration, missing assets, and corrupted plug-in chunks need broader state-machine coverage. |
| Native UI and hardware | Preview verification separates API tests from observed native interaction. | OS mouse delivery to the piano roll was inconclusive. No physical round-trip latency, clock drift, hot-plug, deadline or input-permission measurements are established. |
| Real-time safety | Owned DSP allocation interception and static helper audit exist. | This is not a whole-host no-lock/no-allocation proof. The dependency callback audit already identifies locks and recording fallback allocations. See `docs/realtime-safety.md`. |

The pan-law finding follows directly from the pinned open source engine, including its own hard-pan tests, rather than speculation about the reference binary. [Pinned engine audio utility source](https://github.com/Tracktion/tracktion_engine/blob/07e2d674884293f1a6c8f35fb8d1b9f469ffa41f/modules/tracktion_engine/utilities/tracktion_AudioUtilities.cpp#L231). In particular, changing the engine to its `PanLaw3dBCenter` option alone is not a complete correction: that option attenuates center relative to its extremes. Halftrack must deliberately define normalization and test all intermediate positions.

## Reproducible comparison protocol

The following is a proposed test design derived from the SDK contracts and current gaps; its tolerances are engineering choices, not claims supplied by the reference vendor.

For each case, save a machine-readable manifest containing reference application version/build, Halftrack Git commit, OS/CPU architecture, compiler/options, plug-in format/identifier/version, plug-in state digest, sample rate, block size, channel layout, tempo map, source hashes, start position, render length, gain/pan law, compensation and monitoring modes, quality/oversampling modes, dither, normalization, random seed availability, and expected tail. Pin generated stimulus code as well as the generated audio hash. Use generated signals or user-authorized material, and keep each result attached to the exact configuration that produced it.

Run each reference fixture at least three times first. If the reference differs from itself, identify the varying component (random seed, free-running phase, dither, hardware clock, plug-in mode, external input) before interpreting cross-application error. A self-varying target needs statistical or bounded waveform criteria; it cannot supply a single universal sample-word oracle.

Capture raw output and report two comparisons: **unaligned**, which exposes timing differences, and **aligned by a separately measured integer delay**, which can isolate signal-processing differences. Do not auto-fit arbitrary fractional delay, gain, EQ, or time warping and then report a match: that can hide exactly the defect under investigation. Include the entire specified render window and tail. If a test deliberately warms up, declare and retain its warm-up interval as a separate result.

Use maximum absolute error, RMS error, residual peak in dBFS, number/location of unequal samples, first/last activity sample, channel crossfeed and, where useful, relative RMS error. For a true null, require zero decoded-sample residual under the declared encoding. For tolerance-based paths, specify a threshold before running, save the worst failing window, and keep both raw and aligned errors. Spectral comparisons and listening supplement timing/null tests; a matching magnitude spectrum alone does not establish matching phase or transients.

| Proposed fixture | Stimulus and cases | Required observable |
| --- | --- | --- |
| Transparent path | Silence, impulse at beginning/middle/end, DC, alternating samples, low-level sine, seeded noise; no DSP/fades/dither/rate change | Exact duration/channel order and whole-window PCM identity when the chosen path promises transparency |
| Pan and mix | Separate left-only/right-only impulses; mono and stereo; pan positions -1 to +1 in 0.1 steps; quiet, unity and high gain; multiple correlated/uncorrelated tracks | Explicit 2×2 channel matrix, center/extreme gain, curve, sum order/error, clip/limiter behavior |
| Discontinuities | Abrupt clip start/end, split/rejoin, adjacent clips, gap of one sample, seek, loop crossing | Declared fades, no unintended gaps/duplicates, exact first/last sample, documented smoothing |
| MIDI scheduling | Events at block offsets 0, 1, N-1, N; adjacent same-pitch off/on, overlapping same key, pedal, stop, seek and loop wrap | Received sample offset/order and note-lifetime trace; no stuck or duplicate notes |
| Tempo mapping | Integer/fractional BPM, long duration, boundaries not aligned to block; tempo/meter changes when supported | Beat-to-sample rounding contract and bounded cumulative error; correct transport context |
| PDC | Parallel paths with fixture latency 0, 1, 63, 64, 511, 512, 2048 samples; nested buses/sends/returns; latency changes while stopped/playing | Impulses align exactly according to selected compensation mode; automation and context offsets recorded separately |
| Monitoring/record placement | Synthetic input with independently known timestamps and nonzero reported driver latencies; monitor off/on/auto | Exact recorded sample count/content and timeline insertion offset; no feedback or duplicated monitoring |
| Offline versus callback | Same initial state and event schedule, identical sample rate, controlled block schedule; separately exercise declared mode differences | Null when algorithms promise it; otherwise explicit mode-dependent difference with no accidental truncation |
| DSP response | Impulse, logarithmic sweep, multitone, step and noise at several amplitudes; attack/release bursts; parameter steps/ramps | Frequency/phase response, harmonic/intermodulation products, envelope timing, smoothing, headroom and tail |
| Synth | Every supported pitch/velocity endpoint, waveform/filter/ADSR grid, voice-steal stress, repeated notes and sustain order | Tune, phase/reset policy, aliasing/noise, envelopes, note priority and deterministic repeatability |
| State and undo | Operation sequences with undo-to-baseline, redo-to-final, save/reopen, interrupted/failed saves | Semantic project equality, stable identities, restored plug-in sound/state, correct dirty flag and atomic failure preservation |
| Lifecycle/error | Missing plug-in, failed scan, hung scanner, changed I/O layout, invalid state, repeated editor open/close | Bounded failure, preserved project/audio ownership, correct UI recovery and diagnostics |

For nonlinear, modulated or stateful effects, one impulse response cannot characterize the device. Test amplitude, history, phase, and parameter trajectory as independent axes. For stretching, separately measure transient timing, pitch, sustained-tone artifacts and behavior at ratio 1; using the same general algorithm category does not imply identical output.

## Plug-in and transport contracts that matter

VST3 delivers timing context per processing block, including sample position, musical position and validity flags. The SDK explicitly permits hosts to differ in how they split blocks around loop discontinuities. Therefore two compliant hosts can produce different context histories for the same timeline. The comparison fixture must record the actual history, not infer it from a moving playhead. [VST3 ProcessContext](https://steinbergmedia.github.io/vst3_doc/vstinterfaces/structSteinberg_1_1Vst_1_1ProcessContext.html).

VST3's processing interface allows varying block lengths, parameter queues, state lifecycle transitions, and zero-buffer parameter flushing. Its official processing guidance distinguishes offline operation, defines latency-change notifications and makes bypass handling the plug-in's responsibility. Build a probe plug-in that records context, sample-offset events, parameters, bus activation and lifecycle into a bounded preallocated queue; drain it outside the callback. A probe compiled directly against the VST3 interface avoids mistaking an abstraction wrapper's behavior for the host's raw contract. [VST3 API](https://steinbergmedia.github.io/vst3_dev_portal/pages/Technical%2BDocumentation/API%2BDocumentation/Index.html), [VST3 processing FAQ](https://steinbergmedia.github.io/vst3_dev_portal/pages/FAQ/Processing.html).

CLAP also defines sample-offset events and sorted delivery. Its note IDs, note-expression messages and transport updates have their own semantics; for example, a CLAP note-on with velocity zero is valid, unlike a MIDI 1.0 zero-velocity note-on convention. Preserve the source event dialect instead of silently losing information through a lowest-common-denominator MIDI adapter. [CLAP events](https://github.com/free-audio/clap/blob/main/include/clap/events.h), [CLAP process structure](https://github.com/free-audio/clap/blob/main/include/clap/process.h).

CLAP explicitly permits higher-cost processing in offline mode, and describes a restart/activation protocol for latency changes. Test both modes and the protocol. These contracts do not imply matching behavior with a different plug-in format. [CLAP render extension](https://github.com/free-audio/clap/blob/main/include/clap/ext/render.h), [CLAP latency extension](https://github.com/free-audio/clap/blob/main/include/clap/ext/latency.h).

Plug-in state includes more than visible parameters: CLAP's state extension explicitly includes non-parameter data. Save/restore and duplication fixtures must change such data too. Do not assume a vendor's AU, VST3 and CLAP state chunks or parameter IDs are interchangeable merely because the product name matches. Treat each format/build as a distinct test target until a documented migration contract is verified. [CLAP state extension](https://github.com/free-audio/clap/blob/main/include/clap/ext/state.h).

AU is an Apple platform integration, so native AU hosting is not a symmetric Windows/Linux feature. Apple documents AUv2/v3 host availability on its platforms. Keep the shared host model portable, with explicit format availability and missing-format behavior. Apple's AU latency property reports signal-processing delay in seconds, excluding intentional effect decay, which reinforces the need to keep latency and tail separate. [Apple host integration](https://developer.apple.com/documentation/audiotoolbox/incorporating-audio-effects-and-instruments), [AU latency](https://developer.apple.com/documentation/audiotoolbox/auaudiounit/latency?changes=_7&language=objc).

## Platform, numerical and hardware limits

Compiler floating-point policy is observable audio behavior. Clang documents different choices for reassociation, contraction into fused operations, approximate functions, signed zero and denormal handling. **Inference:** identical C++ expressions and plug-in settings do not alone guarantee identical ARM/x86 or compiler-version output. Record these policies, compare identical builds first, then vary architecture/compiler as a separate axis. Do not enable aggressive floating-point flags in the name of optimization before retaining regression evidence. [Clang floating-point controls](https://clang.llvm.org/docs/UsersManual.html#controlling-floating-point-behavior).

Run core signal tests initially at 44.1, 48 and 96 kHz, then supported extremes. Use blocks 1, 32, 64, 127, 256, 511, 512, 1024 and varying sequences where the interface supports them. The odd sizes are chosen to reveal boundary assumptions. A deterministic built-in synth should retain the same result across legal partitions for the same per-sample event schedule; an arbitrary external plug-in may legitimately depend on its declared mode or processing contract, which must be recorded rather than concealed.

Device latency, plug-in latency and audible round-trip latency are separate measurements. JUCE exposes reported input/output delay and OS xrun counts, but notes that xrun accounting can differ from callback-duration estimates. Use a physical cable/digital loopback test to measure actual round-trip offset and variation, on a deliberately chosen device, with monitoring arranged to avoid a feedback loop. Do not infer hardware latency from buffer size alone or from the current zero-latency synthetic fixture. No microphone capture is needed for the automated suite. [JUCE device contract](https://docs.juce.com/master/classjuce_1_1AudioIODevice.html).

The reference's published compensation behavior includes mode-dependent exceptions for monitoring and routing. Its visible meters can also lead delayed audio. **Inference:** matching a generic “PDC on” switch is insufficient; routing topology, monitored tracks, automation, and displayed meters require separate cases. [Official compensation FAQ](https://help.ableton.com/hc/en-us/articles/209072409-Delay-Compensation-FAQ).

For deadline tests, preserve callback-budget distributions and OS underrun evidence under controlled track counts, disk activity, editor animation and plug-in load. Allocation/lock instrumentation can perturb timing, so use separate correctness-instrumented and production-timing runs. Report maximum and percentile callback times against the relevant device deadline, plus missed deadlines and test duration; a CPU meter average is not enough.

## Highest-value next implementation work

1. Add an exact mixer transfer-matrix regression and deliberately choose/persist pan normalization. This addresses a source-confirmed mismatch already missed by current tests.
2. Extend generated recording fixtures to configurable sample rates, variable block sizes and nonzero latencies. Compare exact captured PCM/timeline placement, not only magnitude and broad duration.
3. Add a dedicated event/context probe and a latency/tail fixture, with separate format wrappers. Begin with VST3, then verify AU independently; CLAP requires its actual adapter before any support claim.
4. Compare complete transparent renders including boundaries, and compare deterministic callback output with offline output from identical initial state.
5. Add state-machine sequences and native-input checks for the piano editor; preserve all known inconclusive results until reproduced.
6. Build the paired reference corpus feature by feature. Record **specified**, **implemented**, **self-tested**, **reference-compared**, and **platform/hardware-verified** as separate statuses. A single percentage obscures which evidence actually exists.

These steps create a measurable route toward close behavior. Binary analysis, if separately pursued, should answer a concrete unresolved question and produce a testable hypothesis; it cannot replace this evidence or turn an untested draft into an exact clone.
