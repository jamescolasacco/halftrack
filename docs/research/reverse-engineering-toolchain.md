# macOS ARM64 reverse-engineering toolchain

Research date: 2026-10-13. Official primary sources only. This report is web research; no proprietary application was inspected, modified, executed, or decompiled for this report, and no tools were installed. The latest user instruction explicitly supersedes the earlier user ban on binary analysis. Root owns any corresponding policy and scope changes.

## Recommended tool order

Use LLVM object inspection for an inventory, Ghidra for selected static analysis, and LLDB for focused runtime questions. Keep Rizin or radare2 as a second parser/disassembler when a finding is uncertain. Binary similarity tools become useful after there are two comparable versions or annotated function sets. These are analysis tools, not a pipeline that restores an original C++ project or proves an exact replacement.

## Ghidra installation and batch analysis

Pin the official **12.1.4 release archive**, rather than the repository's moving default branch or its source-code ZIP. The tagged release guide requires **64-bit JDK 21**. It lists macOS ARM64 under platforms requiring **user-built native components**, rather than among the included native binaries. Build these with Xcode/Command Line Tools and Gradle 8.5+ or the supplied wrapper, using `buildNatives` from `support/gradle`. The current default-branch README says JDK 25; that is a development-branch requirement and should not be silently substituted for the released version. Release documents list Python 3.9–3.14 for debugger/PyGhidra support. A Java-only headless script avoids that optional Python integration. Sources: [tagged Getting Started](https://github.com/NationalSecurityAgency/ghidra/blob/Ghidra_12.1.4_build/GhidraDocs/GettingStarted.md), [current development README](https://github.com/NationalSecurityAgency/ghidra).

The release page publishes SHA-256 `ddac49f903da9d5bac833e5cc79395098b9c33cfd3279be5f31bd00387d2d4db`. Verify the selected release asset against the maintainer's published value before execution; the initial research review did not download it. Subsequent download, hash verification and local execution are recorded in [local results](reverse-engineering-results.md). Source: [12.1.4 release](https://github.com/NationalSecurityAgency/ghidra/releases/tag/Ghidra_12.1.4_build).

Headless analysis supports importing files, processing an existing project, pre/post scripts, timeouts, and limiting CPU use. Use a bounded function selection and record failure/timeout status rather than dumping the whole program and declaring it recovered. The installed release's `support/analyzeHeadlessREADME.html` is the authoritative command reference for that release; the [online headless README](https://github.com/NationalSecurityAgency/ghidra/blob/master/Ghidra/RuntimeScripts/support/analyzeHeadlessREADME.md) is the moving development reference.

For an export script, use `DecompInterface.openProgram`, then `decompileFunction` per selected function with a finite timeout, check completion/error status, and dispose of the interface. The API exposes both C-like text and the high-level syntax representation. Analysis completion only means the tool produced a result; it does not certify correct inferred types or equivalence to source. Source: [DecompInterface API](https://ghidra.re/ghidra_docs/api/ghidra/app/decompiler/DecompInterface.html).

## Focused LLVM and LLDB usage

`llvm-objdump --macho` can inspect universal headers, architecture slices, linked dylibs, runtime search paths, binding/chained fixups, exports, function starts, and disassembly. `llvm-nm` displays symbols, while `llvm-otool` provides Mach-O-specific dumps. `--demangle` improves surviving C++ names; a missing symbol table is not restored by demangling. Sources: [llvm-objdump](https://llvm.org/docs/CommandGuide/llvm-objdump.html), [llvm-nm](https://llvm.org/docs/CommandGuide/llvm-nm.html), [llvm-otool](https://www.llvm.org/docs/CommandGuide/llvm-otool.html).

LLDB supports breakpoints, thread backtraces, register and memory inspection, stepping, and command scripting. Its source-level views depend on usable debug information. Use fresh generated test projects for observations. Record application build, OS, device configuration, sample rate, block size, and the exact action sequence. This recording scheme is our proposed experiment design, not a claim from the debugger vendor. Debugger attach availability for the installed application has not been tested, and this report does not recommend changing OS protections or modifying the application's signature. Source: [LLDB tutorial](https://lldb.llvm.org/use/tutorial.html).

## What decompilation cannot establish

- **Original source recovery:** optimized machine code does not retain the complete source organization, names, comments, templates, or build settings. LLVM describes variables being promoted, moved, and optimized away even when debug metadata exists. Our inference: a stripped optimized C++ application requires reconstructed types, object layouts, virtual-call targets, and control-flow meaning; tool-generated names are hypotheses. Source: [LLVM source-level debugging](https://llvm.org/docs/SourceLevelDebugging.html).
- **DSP bit equality:** a similar formula is insufficient. SIMD layout, reduction order, fused operations, denormal behavior, math-library implementations, state initialization, parameter smoothing, latency, and block boundaries can affect output. LLVM specifically documents floating-point reduction order and fast-math tradeoffs. Our inference: compare deterministic impulses, sweeps, silence, steps, MIDI timing, and parameter transitions at multiple rates/block sizes, reporting numerical error and timing separately. Source: [LLVM vectorization](https://llvm.org/docs/Vectorizers.html).
- **Behavioral completeness:** static call graphs do not enumerate every reachable UI state, keyboard gesture, automation edge case, plug-in failure, or hardware interaction. A parser accepting a file does not verify a correct import. This is an engineering inference: combine static hypotheses with repeatable runtime and rendered-audio observations; attach each claim to a specific tested case.
- **Missing dependencies and data:** the main executable can import behavior from OS frameworks, plug-ins, helper processes, and separate libraries. Its linked-image inventory helps locate boundaries, but does not make those components interchangeable. Our inference: track each boundary explicitly and do not treat external calls as recovered implementations. Source: [Mach-O dependency and binding inspection](https://llvm.org/docs/CommandGuide/llvm-objdump.html).
- **Cross-platform identity:** decompiling one ARM64 macOS build provides evidence about that build. It does not recover a Windows implementation, all versions, or a portable build system. This is an inference from architecture-specific instructions, dependencies, and compilation differences.

BinDiff identifies identical/similar functions and supports transferring labels and comments. [Its integration matrix](https://github.com/google/bindiff/blob/main/docs/disassemblers.md) distinguishes complete integrations from Ghidra's manual workflow. Our recommendation: use it to compare adjacent versions of the same binary after establishing a stable baseline. Comparing a new JUCE/Tracktion implementation directly to an unrelated optimized binary is a poor overall equivalence metric: graph dissimilarity can coexist with matching behavior, and graph similarity does not prove matching outputs. Source: [BinDiff purpose and use cases](https://github.com/google/bindiff).

## Proposed evidence workflow and unresolved facts

1. Verify actual installed tool versions and target architecture/build metadata; retain hashes and version identifiers, not executable redistribution.
2. Create one generated reference project per behavior and establish deterministic observation inputs.
3. Investigate one narrow discrepancy at a time with object metadata, selected static functions, and runtime observations where useful.
4. Write a behavior specification with confidence levels and observable acceptance criteria; distinguish measurement, inferred meaning, and unknowns.
5. Implement and test against those criteria on both supported desktop targets; expand the corpus when a discrepancy appears.

Unknowns not settled by web research: the target's symbol/debug-info availability; actual compiler settings; processor-extension use; helper/library boundaries; whether attach is permitted; analysis duration and memory footprint; compatibility of BinDiff 8 with the exact Ghidra 12.1.4/BinExport build; and the amount of behavior identifiable from selected functions. None should be represented as a verified fact before measurement. No tool surveyed provides a defensible promise of zero differences across every function, input, device, and platform.
